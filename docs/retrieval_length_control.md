# Контроль длины retrieval-ответа: 32 против 8 токенов

## Почему это требуется

В первой серии (`n=40`, `passage_retrieval_en`) все ответы достигли
предела 32 токена. Официальная метрика `retrieval_score` учитывает **все**
числа в ответе, поэтому числа в избыточных продолжениях могут испортить
результат даже при верном начале ответа.

Диагностическая точность **первого номера**:

| Cache | Правильный первый номер | Официальный retrieval_score |
|---|---:|---:|
| Dynamic | 33/40 = 82.5% | 80.42% |
| INT4 g16 | 33/40 = 82.5% | 81.67% |
| INT4 g64 | 25/40 = 62.5% | 45.23% |

У g64 имеются как ошибки в начале ответа, так и правильные первые
номера, за которыми следуют неправильные числа. Это **не** означает,
что разность двух агрегированных процентов является строгим
разложением ошибок по причинам.

## Гипотеза

При сокращении длины генерации до 8 токенов официальный балл
`passage_retrieval_en` может повыситься, особенно у `INT4 g64`,
поскольку из ответа исчезнут некоторые повторы и посторонние числа.
Но начальные неверные ответы (например, `88` вместо `8`)
не должны исправляться только от сокращения лимита.

## Контролируемая постановка

- Те же 40 подготовленных примеров `passage_retrieval_en`.
- Та же Qwen3-1.7B и те же `Dynamic`, `INT4 g16`, `INT4 g64`.
- Те же входные токены; сравнение по `input_ids_sha256`.
- Те же настройки HQQ и greedy decoding.
- **Единственное намеренное изменение** — лимит новых токенов:
  `32 -> 8`.
- Ответы новой серии сохраняются отдельно под
  `results/short_answer/8tokens/`, старые файлы не изменяются.
- Вся метрика считается официальной функцией LongBench
  `retrieval_score`, без изменения кода оригинальной метрики.

Это **диагностическая серия на тех же примерах**, а не независимое
подтверждение на новых данных. После неё потребуется held-out набор
задач для проверки воспроизводимости.

## Как выполнить на login-узле ВШЭ

```bash
cd ~/kv-cache-longbench-pilot
git pull --ff-only
source cluster.env.example
python -m unittest discover -s tests -v
mkdir -p logs results/short_answer/8tokens
sbatch --export=ALL,MODEL_PATH="$MODEL_PATH" slurm/retrieval_short_answer.sbatch
```

Запомнить ID задания из вывода. Затем проверить очередь и коды завершения:

```bash
squeue -u "$USER"
sacct -j JOBID --format=JobID,State,ExitCode,Elapsed
```

Когда все три Slurm tasks завершатся успешно:

```bash
wc -l results/short_answer/8tokens/*.jsonl
python -m src.analyze_retrieval_prefix \
  --results-dir results/short_answer/8tokens \
  --out results/diagnostics/retrieval_first_number_8tokens.csv
python -m src.compare_answer_lengths
```

Должны появиться три файла по 40 строк. Скрипт сопоставления проверяет,
что task IDs, hash входных токенов, model ID, cache и лимиты генерации
совпадают ожидаемым образом. При расхождении останавливается.

## Фактический результат контрольной серии

Три конфигурации завершили генерацию всех 40 ответов.
Исходные и контрольные задания совпали по input hashes,
а первый извлечённый номер оказался неизменным в **0 из 40**
случаев изменения для каждого cache (то есть совпал у всех).

| Cache | Оценка при 32 токенах | Оценка при 8 токенах | Разница, п.п. |
|---|---:|---:|---:|
| Dynamic | 80.42% | 82.50% | +2.08 |
| INT4 g16 | 81.67% | 82.50% | +0.83 |
| INT4 g64 | 45.23% | 62.50% | +17.27 |

Парные 95% bootstrap-интервалы для изменения `8−32`:
Dynamic [0.00; +5.83], g16 [0.00; +2.50],
g64 [+5.00; +29.55] процентных пункта.

**Интерпретация:** сокращение ответа особенно улучшает g64:
ошибки при продолжении ответа и лишние числовые фрагменты
ухудшали официальную оценку. Однако и при восьми токенах g64
на 20 п.п. хуже Dynamic/g16 (62.5% против 82.5%), то есть
ранние ошибки retrieval тоже сохраняются.

Контроль выполнен на **тех же 40 заданиях**: это анализ
формата/продолжения, не независимая проверка на новых примерах.
Следующая серия: [80 новых заданий на датасет](heldout_first_run.md).

## Что считать подтверждением гипотезы

Сравнить внутри каждого cache:

- официальную метрику при 32 и 8 токенах;
- парную разность `8−32` и bootstrap-интервал;
- не изменилось ли первое названное число.

Если g64 улучшится заметно, но отстанет от g16 даже после сокращения
ответа, это поддержит **оба** эффекта: ошибки в первоначальном retrieval
и ошибки в продолжении. Если короткий ответ не улучшит метрику,
возникнет необходимость исследовать более ранние ошибки.

Не переносить результаты контроля длины на QA автоматически:
для длинных текстовых ответов восемь токенов часто недостаточно.
