# LongBench: полная кривая SmolLM3-3B по q_group_size

Дата: 25 октября 2026 года. Серия из **400 генераций**
(80 задач `passage_retrieval_en` × Dynamic/g16/g32/g64/g128).

## Главный результат

Для SmolLM3-3B на одних и тех же 80 заданиях LongBench
средний официальный `retrieval_score` почти сохраняется при всех
четырёх настройках HQQ INT4 с `q_group_size=16, 32, 64, 128`:

| Cache | Официальный retrieval_score | Заданий с нулём | Лимит генерации 32 токена | Средняя длина |
|---|---:|---:|---:|---:|
| Dynamic | **93.750%** | 5/80 | 7/80 | 5.8 |
| INT4 g16 | **93.750%** | 5/80 | 6/80 | 5.2 |
| INT4 g32 | **92.500%** | 5/80 | 7/80 | 5.6 |
| INT4 g64 | **93.125%** | 5/80 | 8/80 | 6.5 |
| INT4 g128 | **92.500%** | 5/80 | 6/80 | 6.0 |

Парные разности (кандидат − базовая конфигурация):

| Сравнение | Δ, процентных пунктов | 95% percentile bootstrap |
|---|---:|---|
| g16 − Dynamic | 0.000 | [0.000; 0.000] |
| g32 − Dynamic | −1.250 | [−3.125; 0.000] |
| g64 − Dynamic | −0.625 | [−1.875; 0.000] |
| g128 − Dynamic | −1.250 | [−3.125; 0.000] |
| g32 − g16 | −1.250 | [−3.125; 0.000] |
| g64 − g16 | −0.625 | [−1.875; 0.000] |
| g128 − g16 | −1.250 | [−3.125; 0.000] |
| g64 − g32 | **+0.625** | **[−1.250; +3.125]** |

Точные значения в таблице взяты из дискретных баллов,
средних по 80 заданиям; CLI округляет их до двух знаков.
g64 формально оказывается выше g32, однако интервал охватывает
ноль. **Монотонного ухудшения с ростом group size нет**, и
наблюдение не означает, что g64 «улучшает» модель.

**Корректная интерпретация:** сильной деградации качества при
g64 и g128 на этой retrieval-выборке не наблюдаем.
Интервалы разниц включают ноль, что **не доказывает
статистическую эквивалентность**. По 5/80 нулевых баллов
во всех пяти случаях — это агрегат: ещё нужно убедиться,
совпадают ли ошибки в одних и тех же заданиях.

## Контраст с Qwen3-1.7B

В уже выполненной независимой held-out серии Qwen3-1.7B
применены те же **исходные 80 задач** LongBench, но
с собственным токенизатором Qwen3:

| Cache | Qwen3-1.7B | SmolLM3-3B |
|---|---:|---:|
| Dynamic | 80.625% | 93.750% |
| INT4 g16 | 78.271% | 93.750% |
| INT4 g32 | 79.271% | 92.500% |
| INT4 g64 | 39.512% | 93.125% |
| INT4 g128 | 23.853% | 92.500% |
| g64 − Dynamic | −41.113 п.п. | −0.625 п.п. |
| g128 − Dynamic | −56.772 п.п. | −1.250 п.п. |

У Qwen3 g64 очень сильно ухудшила результат относительно
её собственной базы; у SmolLM3 относительное снижение
в баллах LongBench минимально. См. также
[полную кривую Qwen3 по четырём размерам групп](group_ablation_results_80.md).

**Нельзя приписывать отличие одной только архитектуре.**
Модели отличаются числом параметров (1.7B vs 3B),
обучением, токенизаторами и поведением при генерации.
Одинаковые задачи означают одинаковые оригинальные тексты
и `source_index`, **но не одинаковые токеновые последовательности**.
Официальные raw-промпты применялись без chat template
для согласованности с исходной серией.

## Что именно измеряли

- SmolLM3-3B: `HuggingFaceTB/SmolLM3-3B`.
- FP16-веса на NVIDIA V100, batch size 1.
- Greedy-decoding, один prefill + последовательный decode.
- `transformers.QuantizedCache` с backend HQQ,
  `nbits=4`, `axis_key=axis_value=1`,
  `residual_length=128`, группы 16, 32, 64 и 128.
- Входы: фиксированная held-out выборка LongBench
  (80 задач из `passage_retrieval_en`, seed 2027,
  без пересечения с пилотом Qwen3 n=40).
- Метрика: оригинальная функция LongBench `retrieval_score`
  из закреплённого локального checkout.
- Интервалы: paired percentile bootstrap (2000 повторов,
  seed 2026), пары составлены **внутри** SmolLM3
  на совпадающих task IDs и хешах входных token IDs.
- Выходы: `results/families/smollm3-3b/retrieval80/`
  на кластере; агрегаты:
  `results/families/smollm3-3b/summary/retrieval_scores.csv`
  и `retrieval_pairs.csv`.

## Почему это не просто «SmolLM3 лучше Qwen»

Qwen3-1.7B на тех же raw LongBench-подсказках иногда
доходила до лимита генерации и давала лишние номера/повторы.
У SmolLM3-3B большинство ответов короткие (5–7 токенов).
Официальный `retrieval_score` чувствителен к лишним числам,
а значит различия в поведении декодера могут влиять
на наблюдаемые баллы **независимо от качества поиска ответа**.

Нужно дополнительно проверить первые числа в предсказаниях,
повторы, ошибки продолжения и распределение длин входа
в двух моделях. Без этого нельзя утверждать,
что более крупные группы меньше искажают *внутренние*
представления KV Cache именно у SmolLM3.

## Следующие шаги

1. **Проверить фактические ошибки и их источник**:
   первое число, лишние числа в продолжении, достигнутый
   лимит генерации, совпадение плохих заданий, peak GPU memory.
2. Проверить переносимость **между типами задач**:
   `multifieldqa_en` с Dynamic/g16/g64. Сначала sanity check,
   поскольку raw-промпты могут по-разному работать у моделей.
3. Проанализировать, где именно расходятся ответы:
   первая найденная цифра, дополнительные цифры, cap,
   совпадение ошибок и длина входа.
4. Рассчитать trade-off памяти по `peak_gpu_gib` внутри
   SmolLM3, с явным уточнением, что это пиковая
   выделенная CUDA-память, а не изолированный размер KV Cache.

## Воспроизведение анализа

На login-узле кластера:

```bash
python -m src.score_family_retrieval \
  --caches dynamic int4_g16 int4_g32 int4_g64 int4_g128
```

Анализ использует пять JSONL по 80 ответов в
`results/families/smollm3-3b/retrieval80/`.
Сами экспериментальные JSONL остаются на кластере,
поэтому для воспроизводимости нужна отдельная резервная копия.
