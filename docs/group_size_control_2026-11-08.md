**Серия group_size_v1: граница устойчивости между g16 и g64.**

Мотивация — [завершённая диагностика](protocol_v1_diagnostics_2026-11-08.md):
провал Qwen проявляется уже в первом токене split QA и почти всегда без refresh.
Следующая проверка: сохраняет ли промежуточная группа 32 качество g16 или уже
показывает усиление потерь при обработке вопроса через приближённый cache?

| Ось | Значения |
|---|---|
| Модели | Qwen3-1.7B, Qwen3-4B |
| Задачи | passage_retrieval_en, multifieldqa_en |
| Порядок prefill | single_prefill, context_then_question |
| Новая конфигурация | HQQ INT4 g32, residual_length=128 |
| Данные | те же 80 вопросов и token IDs из protocol_v1 |
| Объём | 8 ячеек × 80 = 640 новых ответов |
| Smoke | 8 ячеек × 3 = 24 ответа, отдельный каталог |

Сохраняются native chat без thinking, FP16/SDPA, пределы входа/ответа,
axis_key=axis_value=1 и локальные веса. SmolLM3 в этот запуск не включён:
первый вопрос — положение границы падения у двух Qwen. Сравнение семейства
и перенос на новые документы потребуют последующих серий.

Dynamic/g16/g64 берутся из завершённых полных JSONL protocol_v1. Новый runner
проверяет совпадение входов, manifest, артефактов модели, версий пакетов,
типа GPU/CUDA и хешей общего кода генерации. Содержимое исходных результатов
закрепляется отдельным SHA-256 в provenance каждого нового запуска.
При несовпадении условий сравнение останавливается. Старые файлы не меняются.
Это экономит повторный расчёт baselines, но не измеряет вариативность между
повторными GPU-запусками; окружение нельзя обновлять между сериями.

Подготовленные token IDs повторно не создаются. Нужны полная матрица
`results/protocol_v1/full`, прежние `data/prepared/protocol_v1` и локальные веса.
Конфигурация: [experiments/group_size_v1.json](../experiments/group_size_v1.json).

На login-узле:

```bash
cd ~/kv-cache-longbench-pilot
git pull --ff-only
module load python
conda activate kvcache
bash tools/start_group_size.sh smoke
```

Helper проверяет входы, baseline, версии пакетов и общий код до отправки Slurm.
Полученный job ID относится к восьми ячейкам; максимум два задания одновременно,
одна V100 на задание. Логи: `logs/lb-g32-v1-<job>_<cell>.out` и `.err`.
Порядок ячеек: 0–3 Qwen3-1.7B, 4–7 Qwen3-4B; внутри модели retrieval single/split,
затем QA single/split. Дефолтные пути весов совпадают с protocol_v1;
переопределения `KV_MODEL_ROOT`, `QWEN17_MODEL_PATH`, `QWEN4_MODEL_PATH` сохраняются.

После завершения восьми smoke-ячеек:

```bash
python -m src.score_group_size --phase smoke
```

Scorer проверяет полную матрицу, одинаковое подмножество вопросов, связь с
неизменёнными baselines и совпадение первого токена single_prefill с Dynamic.
Качество на трёх вопросах не обобщается. Реальный HQQ g32-путь должен пройти
эту проверку на V100; локальные CPU-тесты её не заменяют.

После успешного smoke и просмотра ответов:

```bash
bash tools/start_group_size.sh full
```

Helper и каждый GPU-процесс отдельно проверяют smoke. Полный запуск сохраняет
80 ответов в ячейке отдельно от smoke; автоматического перехода к нему нет.
Повтор той же команды продолжает недостающие ответы при совпадении fingerprint.
Если процесс ещё пишет ячейку, вторая копия останавливается по файловой блокировке.

После завершения:

```bash
python -m src.score_group_size --phase full
cat results/group_size_v1/summary/full/paired_contrasts.csv
```

Результаты: `results/group_size_v1/{smoke,full}/`; сводки —
`results/group_size_v1/summary/{smoke,full}/`. Основные сравнения:
g32−Dynamic отдельно для каждой модели/задачи/протокола. Дополнительные:
g32−g16, g32−g64, изменение потерь single→split и прямое различие потерь
между двумя размерами Qwen. CI считаются парным bootstrap по документам,
2 000 повторов, seed 2026; без поправки множественных сравнений.

Это продолжение на ранее изученной выборке. Оно уточняет гипотезу,
но не является независимой проверкой на новых документах. Не выбираем
конфигурацию по нескольким smoke-примерам и не называем качество близким
к Dynamic только на основании CI, включающего ноль.
