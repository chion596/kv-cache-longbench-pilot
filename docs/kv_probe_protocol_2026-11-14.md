После повторения split-провала на новых документах проверяем два вопроса:
сохраняется ли ухудшение предсказания номера при общем префиксе ответа и
какой вклад дают приближённые K и V при фиксированных остальных условиях.
Это отдельная диагностика механизма на уже изученных документах,
а не новый LongBench score или независимый подтверждающий тест.

**Выборка и матрица.** Две Qwen3 (1.7B/4B), только retrieval EN и split.
Берём первые 20 source indices **в порядке неизменной expansion_v1 selection**,
без фильтрации по правильности Dynamic, длине ответа или величине потерь.
Промпт, input IDs, контекст и граница split точно совпадают с expansion_v1.
Веса/tokenizer и версии пакетов сверяются с её manifest.

| Политика | K документа | V документа | Размер группы |
|---|---|---|---:|
| dynamic | точные | точные | — |
| k_g32 / k_g64 | HQQ INT4 | точные | 32 / 64 |
| v_g32 / v_g64 | точные | HQQ INT4 | 32 / 64 |
| kv_g32 / kv_g64 | HQQ INT4 | HQQ INT4 | 32 / 64 |

2 модели × 7 политик × 20 документов = **280 основных оценок**.
Smoke — первые три из этих 20: **42 оценки**, плюс **18 дополнительных
сверок реализации**. В full первые три считаются заново, отдельно от smoke.
В одном GPU job загружаем одну модель и последовательно проходим семь политик.

**Подача и измерения.**

1. Prefill документа возвращает исходные K/V, как stock QuantizedCache;
   выбранные стороны сохраняются в HQQ INT4, другая сторона точно в FP16.
2. Подаём исходный вопрос и chat suffix отдельным forward. Первый свободный
   токен только записываем для сверки, в продолжение его не подаём.
3. Во всех условиях принудительно подаём одинаковый текст
   `The abstract is from Paragraph `, затем правильный номер без точки/EOS.
   Модель не выбирает токены продолжения. Префикс не содержит gold-номер.
4. Считаем NLL каждого gold-токена номера в FP32, среднее и сумму NLL,
   а также logit gold-первого токена минус максимальный logit другого
   vocabulary token. Положительная NLL delta означает ухудшение;
   отрицательная margin delta означает ухудшение.

У Qwen номера 1–30 занимают один или два токена; margin первого токена
не измеряет правильность полного номера и не различает номера с одинаковым
начальным токеном. Основная метрика — средняя по токенам NLL полного номера,
затем средняя по документам; сумму NLL сохраняем отдельно.
Пунктуация, EOS и ранжирование всех 30 номеров здесь не оцениваются.

FP16/SDPA, HQQ axis_key=axis_value=1, residual=512. До запуска проверяем
`query + forced prefix + gold target < 512`, корректность токенизации общей
границы префикса и номера. Поэтому question/prefix/target остаются в точном
residual; повторная квантизация документа запрещена во всех слоях.

**Почему это сохраняет связь со stock HQQ.** Селективный cache использует
тот же `QuantizedCache.update`; обходим только quantize/dequantize точной
стороны, сохраняя её tensor. Последовательность первых вызовов K,V и отсутствие
refresh проверяются. Политика both выполняет исходные HQQ-вызовы для обеих сторон.
В smoke для каждого документа/модели:

- both g32/g64 должен дать **точно те же logits gold-продолжения и первый
  токен вопроса**, что исходный stock HQQ;
- обход квантизации обеих сторон должен совпасть с Dynamic;
- источник cache_utils/HQQ, код runner, model manifest, исходные inputs и
  reference JSONL фиксируются хешами. Код/версии/GPU/CUDA между smoke и full
  должны совпасть.

Первый токен вопроса также сопоставляется со старым expansion_v1 и выводится
число несовпадений. Это повторный FP16 forward, поэтому такое несовпадение
показываем отдельно; оно не заменяет обязательную сверку с новым stock forward.
Контроль использует частные методы
[реализации Transformers 5.17](https://github.com/huggingface/transformers/blob/v5.17.0/src/transformers/cache_utils.py),
поэтому успешные локальные CPU-тесты не заменяют HQQ/FP16/CUDA smoke на V100.
Локально проверены настоящие HQQ-вызовы, обход одной стороны, запрет refresh,
совпадение both/stock и выравнивание NLL на маленькой случайной Qwen.

**Контрасты.** Для каждой модели/group считаем парные NLL и margin:
K−Dynamic, V−Dynamic, both−Dynamic, K−V и неаддитивность
`both−K−V+Dynamic`. Интервалы по source context, 2 000 bootstrap,
seed=2026, номинальные 95%, без поправки множественных сравнений.
Это exploratory-проверка на n=20; отсутствие выделившейся delta не означает
эквивалентность. Семейства здесь не сравниваются.

Если both заметно портит NLL и при общем префиксе, расхождение свободного
текста не является единственным объяснением. Если forced-префикс восстанавливает
предсказание номера, это укажет на роль траектории ответа, но ещё не исключит
другие ошибки retrieval. Более сильная K−V delta локализует чувствительность
в этой постановке; она не устанавливает универсальную «главную причину».

**Запуск.** На login-узле:

```bash
cd ~/kv-cache-longbench-pilot
git pull --ff-only
module load python
conda activate kvcache
bash tools/start_kv_probe.sh smoke
```

Helper только читает старую серию, готовит новый `data/prepared/kv_probe_v1/`
и отправляет Slurm-массив 0–1. Пакеты обновлять и модели скачивать не требуется.
После завершения обеих моделей:

```bash
python -m src.score_kv_probe --phase smoke
```

Нужно получить 14 ячеек, 42 оценки, успешные stock/exact-сверки и отсутствие
refresh. До успешного smoke full не отправляем. Затем отдельной командой:

```bash
bash tools/start_kv_probe.sh full
# После завершения:
python -m src.score_kv_probe --phase full
cat results/kv_probe_v1/summary/full/paired_contrasts.csv
```

Slurm: до двух GPU одновременно, по одному на модель, лимит job **2 часа**.
4 GPU-часа — максимум по выделенному времени двух job, **не ожидаемый расход**.
Smoke покажет оценку 280 forward по `probe_sec`; она исключает загрузку модели,
GC, дополнительные сверки и ожидание, и не является сравнением throughput.
При time limit helper можно повторить с той же фазой: совместимые полные
строки пропускаются, изменённые условия/повреждённые файлы отклоняются.
Логи: `logs/lb-kv-probe-v1-<array>_<model>.err` и `.out`.
