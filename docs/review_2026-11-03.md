3. **Главный конфаундер — формат входа и остановка ответа.**

Вход всегда формируется через `tokenizer.encode(..., add_special_tokens=False)`, без chat template. У Qwen3 на n80 все retrieval-ответы достигают 32 токенов; почти все QA — 64. SmolLM3 обычно останавливается значительно раньше. Поэтому сравнение семейств включает различия в следовании формату и продолжении ответа.

Официальный retrieval_score считает долю правильного номера среди всех чисел в ответе: правильный номер в начале с посторонними числами дальше теряет балл. QA F1 также штрафует избыточное продолжение. Это свойства официальных метрик, применённых корректно. Диагностика первого числа/первой строки помогает понять причину потерь, но не заменяет полную метрику.

Деградация Qwen3-1.7B не исчерпывается продолжениями: правильное первое число на retrieval падает с 66/80 у Dynamic до 42/80 при g64 и 37/80 при g128. Вместе с тем первое число может состоять из нескольких токенов; оно не тождественно первому сгенерированному токену.

Следует провести отдельную серию с native chat template и явно отключённым thinking у Qwen3 и SmolLM3. Сохранить содержимое официальной задачи, исходные max_new_tokens и greedy decoding, чтобы не менять сразу несколько факторов. Зафиксировать новые token IDs/хеши, завершающие токены и реальные причины остановки. В текущей raw-серии нет основания утверждать, что thinking был строго отключён штатным переключателем модели.

Источники: `src/prepare_data.py:32`, `src/run_quality.py:54`; [Qwen3 non-thinking](https://huggingface.co/Qwen/Qwen3-1.7B#switching-between-thinking-and-non-thinking-mode), [SmolLM3](https://huggingface.co/HuggingFaceTB/SmolLM3-3B), [официальная метрика](https://github.com/THUDM/LongBench/blob/main/LongBench/metrics.py).

4. **Существенная деталь: первый ответный токен в текущем пути получается до чтения квантованных K/V.**

В Transformers v5.17.0 `QuantizedLayer.update()` при первой инициализации сохраняет квантованные K/V, но возвращает исходные `key_states, value_states`. В `run_quality.py` весь промпт, включая вопрос, подаётся одним prefill. Первый ответный токен берётся из его logits. На последующих forward модель читает деквантованный prompt cache.

Следствия из исходного кода, требующие проверки против реально установленного файла на кластере:

- При сопоставимом численном исполнении первый token ID должен совпадать у Dynamic и HQQ. Если отличается, сначала проверить backend, masks, версии и численную воспроизводимость.
- Лимит в один новый токен практически обходит исследуемое чтение квантованного кэша. Такой тест не подтверждает устойчивость retrieval к квантизации.
- Даже обычный короткий ответ может частично скрыть эффект, если существенная часть ответа помещается в первый токен конкретного tokenizer.
- Нужно сохранять output token IDs и позицию первого расхождения. Повторная токенизация текста с удалёнными special tokens не даёт гарантированного восстановления исходной траектории.

Особенно полезный дополнительный контроль: сначала закэшировать документ, затем отдельным forward подать вопрос и начало ответа. Тогда обработка вопроса и первый ответный токен будут зависеть от квантованного контекста. Это новая постановка использования cache. Для Dynamic следует сначала проверить близость logits и совпадение ответов с обычным prefill на том же полном тексте.

Источник: [Transformers v5.17.0 cache_utils.py](https://github.com/huggingface/transformers/blob/v5.17.0/src/transformers/cache_utils.py#L705).

5. **Residual length сейчас не проверяет многократную переквантизацию.**

После первого prefill весь prompt cache уже квантован. При `residual_length=128` и генерации максимум 32/64 токенов новые decode-K/V не успевают заполнить residual storage до порога повторной квантизации. Поэтому текущий результат нельзя объяснять многократной переквантизацией длинного prompt cache на каждом шаге. Деквантизация и использование приближённого prompt cache при decode действительно происходят.

Sweep `128 → 256 → 512` при тех же коротких ответах в этом коде не проверит содержательно новую гипотезу. Для исследования residual нужны меньшие пороги, например 16/32, или отдельная серия с более длинной генерацией и регистрацией реальных событий переквантизации. Текущий residual_length также не означает сохранение последних 128 токенов исходного документа в FP16 после первого prefill.

7. **Сравнение моделей следует считать прямым контрастом.**

Для одной задачи i определить `d_i(model) = score_i(g64) − score_i(Dynamic)`. Затем сравнить `d_i(SmolLM3) − d_i(Qwen3)`, одновременно ресэмплируя те же source tasks, а для QA — документы. Это проверяет различие чувствительности моделей. Наличие CI ниже нуля у одной модели и CI, включающего ноль, у другой само по себе не является тестом различия этих эффектов.

По опубликованным средним различие потерь составляет около +40.49 п.п. на retrieval и +10.57 п.п. на QA EN в пользу SmolLM3. Прямые CI для этих межмодельных контрастов в репозитории не приведены. Даже статистически надёжный контраст не изолирует архитектуру: различаются размер, обучение, tokenizer и формат поведения.

CI SmolLM3 QA g64−Dynamic [−6.324; +0.885] допускает практически существенное ухудшение. Заявление «качество сохранено в пределах 2 п.п.» этот интервал не подтверждает. Для такой цели заранее выбрать допустимую потерю и применить анализ не меньшей эффективности; при необходимости для эквивалентности задать обе границы. Увеличение bootstrap iterations не заменяет новые документы.

Для retrieval дополнительно нужны таблицы переходов «верно у Dynamic → неверно у quant» и обратных переходов. Одинаковые 75/80 не гарантируют одинаковый состав ошибок. `diagnose_family_retrieval` включает в перечень changed только задачи с изменившимся официальным score; это не полный перечень различий текста или первого номера.

8. **Память и время требуют отдельного сопоставимого измерения.**

`peak_gpu_gib` — `torch.cuda.max_memory_allocated()` за prefill+decode. Оно включает веса, временные тензоры и allocations квантизатора. Оно не равно размеру resident KV Cache. `decode_tok_s` измерен с Python-loop, синхронизациями и различным числом шагов до EOS. Эти поля полезны для диагностики; для вывода об эффективном serving нужен отдельный performance protocol.

По официальным конфигам, для одинаковых 16 384 токенов и FP16 теоретический обычный KV равен:

| Модель | Layers | KV heads | Head dim | Dynamic KV при 16K |
|---|---:|---:|---:|---:|
| Qwen3-1.7B | 28 | 8 | 128 | 1.750 GiB |
| Qwen3-4B | 36 | 8 | 128 | 2.250 GiB |
| SmolLM3-3B | 36 | 4 | 128 | 1.125 GiB |

Формула: `2 × layers × kv_heads × head_dim × tokens × bytes_per_value`. Поэтому меньшая относительная экономия total peak у SmolLM3 ожидаемо может быть связана с другой долей KV и весов. Процент total saving не является сравнением качества самого квантизатора.

Следующий performance block: 3 модели × 4 длины (4K/8K/16K/32K, при успешной проверке памяти) × 5 cache × 3 измеряемых повтора = 180 измерений плюс warm-up. Фиксированное число decode steps; resident KV по уникальным tensor storages после prefill и decode; total allocated/reserved peak; prefill time, TTFT и decode throughput. Весовая точность, attention backend и GPU одинаковы. Вне performance block сохраняется естественная EOS-остановка quality-эксперимента. Подсчёт storages можно перенести из исходного проекта с адаптацией под проверенную версию cache API.

Источники: [Qwen3-1.7B config](https://huggingface.co/Qwen/Qwen3-1.7B/raw/main/config.json), [Qwen3-4B config](https://huggingface.co/Qwen/Qwen3-4B/raw/main/config.json), [SmolLM3 config](https://huggingface.co/HuggingFaceTB/SmolLM3-3B/raw/main/config.json).

Не требуется заново генерировать неизменённые legacy-ячейки, для которых уже есть полные проверенные файлы. Изменение prompt/protocol требует новой серии; старые raw-ответы нельзя смешивать с новыми chat-ответами. Группы g32/g128 добавлять к новой серии после решения основного вопроса, если они уточняют форму зависимости.

Размеры полных исходных наборов ограничены: EN QA — 150, ZH QA и retrieval EN — по 200. После n40+n80 остаётся 30/80/80 новых вопросов соответственно. На проверенном архиве в QA EN остаётся только 17 полностью невиденных context, в QA ZH — 42. Поэтому широкая независимая проверка требует новых документов/датасетов, а не предложения «взять ещё 500 вопросов multifieldqa_en».

Для нового естественного набора сначала проверить Dynamic на небольшой заранее фиксированной группе: если он у пола, выбрать более сильную модель или исправить протокол и объявить новую серию. Не перебирать датасеты до получения удобной величины эффекта. Сохранить ограничение входа и явно показать долю усечения и наличие evidence в сохранённом тексте.

Источники: [официальные размеры и категории LongBench](https://github.com/THUDM/LongBench/blob/main/LongBench/task.md), [официальные max lengths](https://github.com/THUDM/LongBench/blob/main/LongBench/config/dataset2maxlen.json).

10. **Механистическая серия способна дать больший научный вклад, чем ещё много близких model sweeps.**

Первая задача — локализовать первые расхождения, а не сразу разрабатывать adaptive cache. Сохранять token IDs, одинаковый teacher-forced префикс, NLL/logit margins на токенах правильного ответа и ошибки деквантованных K/V по слоям. Отдельно сравнить свободную генерацию и одинаковую историю: после первого свободного расхождения дальнейшие logits условны уже на разных текстах.

Полезные интервенции: квантовать только K, только V, затем оба; временно сохранять ранний/средний/поздний блок слоёв в FP16 или g16 при g64 в остальных. На этапе диагностики достаточно ограниченного числа задач, включая заранее выбранные успешные и неуспешные случаи. Выборку по наблюдаемым ошибкам явно считать диагностической, а не использовать для итогового accuracy.

В HQQ 0.2.8.post1 при axis=1 тензор reshapes в `[-1, group_size]`. Для contiguous `[batch, kv_heads, tokens, head_dim=128]` группы 16/32/64/128 располагаются внутри одного token/head. Поэтому возможен содержательный анализ outlier channels и изменения ошибки при укрупнении группы. Нельзя автоматически переводить названия axis в «квантизацию по токенам/каналам» без проверки реального reshape.

Не следует сохранять все prefill attention matrices на 16K: это квадратичный объём. Для диагностики достаточно выбранных decode positions, отдельных голов/слоёв, K/V summary и ограниченного числа входов.

После локализации можно проверить mixed group size: g16 для небольшого набора чувствительных слоёв, g64 для остальных. Оценивать на новых документах и обязательно сравнивать с простым uniform g32. Научная цель — улучшить quality–memory Pareto frontier, а не только восстановить g64 ценой памяти выше g32.

Источник группировки: проверенный sdist [HQQ 0.2.8.post1](https://pypi.org/project/hqq/0.2.8.post1/), SHA-256 `8fa34c074df43b32acf10173abbc7dfdeff1ae529b673acfc2628a1c9c61fc8a`. Файл `hqq/core/quantize.py`, строки 105–119. Исходник читался без установки пакета.

11. **Другие семейства и сравнение с методами из литературы.**

Qwen3-4B — наиболее выгодный ближайший контроль: веса и smoke уже описаны, постановка продолжает прежнее наблюдение Qwen3 model scaling. Для третьего семейства на близком к SmolLM3 размере Llama-3.2-3B-Instruct полезнее как первый научный контроль, чем только Llama-3.2-1B. Позднее пара Llama 1B/3B вместе с Qwen3 1.7B/4B позволит сравнить несколько размеров в двух семействах. Размеры и обучение всё равно не идентичны.

DeepSeek-R1-Distill-Qwen и Distill-Llama наследуют Qwen/Llama base models. Они полезны для изучения влияния distillation/post-training, но не создают независимую архитектуру DeepSeek. Полноразмерный DeepSeek с MLA требует самостоятельной постановки: storage, совместимость и смысл quantization отличаются от обычных K/V heads. Это более поздняя ветка, не необходимая для проверки текущей гипотезы.

Для сопоставления с другими авторами нужны запуски алгоритмов на своих одинаковых моделях, задачах, входах и бюджете resident KV bytes. Stock HQQ — самостоятельная реализация; его нельзя называть воспроизведением KIVI. Кандидат для прямого сравнения — проверенная реализация KIVI/асимметричной K/V quantization. Это отдельная инженерная задача с проверкой API и backend. При наличии поддерживаемой GPU можно отдельно проверить Quanto; в исходном проекте Quanto 0.2.7 на V100 падал при компиляции kernels, требующих SM80+. Повторять его массовую серию на том же неподдерживаемом пути нецелесообразно.

При сравнении с token eviction, например SnapKV, сопоставлять реальный бюджет KV и качество, а также latency. Равные названия «4 bit» и «25% токенов» не гарантируют равный storage или одинаковую стоимость. Числа из чужой LongBench leaderboard без воспроизведения их protocol пригодны для контекста, но не для заявления о превосходстве своей конфигурации.

Источники: [Llama-3.2-3B-Instruct](https://huggingface.co/meta-llama/Llama-3.2-3B-Instruct), [семейства distilled DeepSeek](https://huggingface.co/deepseek-ai/DeepSeek-R1), [KIVI](https://arxiv.org/abs/2402.02750), [ограничение Quanto в исходном проекте](https://github.com/chion596/kv-cache-efficiency/blob/main/notes/quanto_v100_limitation.md).

12. **Язык и длинный контекст следует исследовать отдельными контролируемыми сериями.**

Уже имеющиеся EN/ZH QA показывают согласованное направление эффекта у Qwen3-1.7B. Они используют разные документы, вопросы и варианты F1, поэтому разницу потерь нельзя причинно приписать языку.

Для языкового эксперимента выбрать одинаковые факты и вопросы в двух языковых версиях; фиксировать длину токенизации, позицию evidence и направление перевода. Для части заданий нужны человеческая проверка перевода и однозначности ответа. Измерять quant−Dynamic внутри каждого языка, затем разницу этих эффектов на парах. Общая exact-match/нормализованная fact-метрика для одних сущностей/чисел облегчает интерпретацию; оригинальные LongBench F1 сохранять отдельно. Одинаковое содержание и одинаковое число токенов — разные контроли; их следует анализировать явно, не добиваясь равной длины удалением нужных доказательств.

Qwen3 удобен как первая модель EN/ZH. У SmolLM3 китайский входит в языки с меньшим объёмом обучения, чем основные шесть, поэтому заранее проверить Dynamic, чтобы не принять низкий baseline за устойчивость к quantization. Добавление русского возможно как отдельная авторская переводная серия, с явным указанием, что это не стандартный LongBench v1.

Для длины сначала использовать имеющиеся `input_tokens`, `full_prompt_tokens` и `middle_truncated`, но не объявлять наблюдаемую корреляцию длины причинной. Нельзя бездумно обрезать LongBench до 4K/8K: вместе с текстом может исчезнуть ответ. Следующий управляемый benchmark — небольшая часть RULER, например multi-key и multi-value retrieval, по 50 новых задач при 4K/8K/16K/32K. Две модели × три cache дают 2 400 генераций. Полный RULER и LongBench v2 пока не обязательны; для v2 особенно важны достаточный baseline и существенно иные длины.

RULER следует подключать через собственный проверенный HF/HQQ runner: запуск через другой inference engine без поддержки выбранного cache не будет измерять тот же объект. Зафиксировать версию генератора и новые task seeds.

Источники: [SmolLM3 языки](https://huggingface.co/HuggingFaceTB/SmolLM3-3B), [NVIDIA RULER](https://github.com/NVIDIA/RULER), [LongBench v1/v2](https://github.com/THUDM/LongBench).

13. **Ресурсы: разумно увеличить объём до нескольких тысяч генераций и десятков GPU-часов.**

В октябрьской части присланного скриншота для строки «Шиловский Никита» видно 7.98 GPU-часа; в других строках — сотни. Это показывает, что текущий расход невелик относительно части участников. Скриншот не показывает свободную квоту проекта, типы GPU во всех расчётах, полезную загрузку и исследовательские задачи участников. Расход других людей не определяет необходимый объём этого исследования.

Ближайший содержательный масштаб: закончить Qwen3-4B, проверить протоколы, затем 3 150 генераций полных retrieval EN + QA EN и ещё 1 800 на одном новом естественном наборе. Получится около 5 000 генераций основной подтверждающей матрицы, плюс ограниченная диагностика. Неизменённые уже выполненные ячейки можно переиспользовать после проверки provenance.

| Среднее фактическое время одной генерации | 3 150 генераций | 4 950 генераций |
|---|---:|---:|
| 10 секунд | 8.75 GPU-часа | 13.75 GPU-часа |
| 30 секунд | 26.25 GPU-часа | 41.25 GPU-часа |
| 60 секунд | 52.50 GPU-часа | 82.50 GPU-часа |

Это арифметические сценарии, а не прогноз измеренного runtime. Добавить загрузку моделей, служебное время и резерв; очередь влияет на календарный срок. Сначала оценить время по реальным логам для каждой модели и распределению входных длин. Формула бюджета: сумма GPU-count × elapsed hours по заданиям.

Текущий runner делает `.to("cuda")` и работает на одном устройстве. Запрос четырёх GPU одному его процессу не ускорит расчёт. Масштабировать независимые ячейки/шарды, сохраняя одну GPU на процесс. Текущий Slurm array уже допускает 2–3 параллельных задачи; дальнейший предел выбирать по квоте проекта и правилам очереди. Суммарные GPU-часы от параллелизма почти не уменьшаются; уменьшается календарное время при наличии свободных устройств.

Повторять deterministic greedy quality run 10 раз с разными seed обычно малоинформативно: seed выборки и seed sampling — разные вещи, а sampling здесь отключён. Для статистики нужны новые задачи/документы. Для performance нужны повторы после warm-up; для воспроизводимости численного пути достаточно выборочного повторного quality контроля.

14. **Что подготовить перед крупной матрицей.**

- Один актуальный статус вместо нескольких противоречащих записей «ещё не выполнено» / «завершено» в README. Сейчас старые инструкции остаются рядом с более новыми отчётами.
- Машиночитаемые aggregate и per-example scores, source IDs, manifest и archive/model/code revisions. Сейчас Git игнорирует весь `results/`, а опубликованные результаты представлены преимущественно Markdown-таблицами. Точное воспроизведение чисел по одному публичному checkout недоступно.
- Зафиксированное окружение: torch/CUDA/Transformers/HQQ и metric dependencies, фактический attention backend. `requirements-extra.txt` содержит только дополнительные зависимости метрик.
- В результатах: output token IDs, stop reason, model/tokenizer revision, HQQ version, code commit, context hash и protocol ID. Местный путь модели не идентифицирует её содержимое.
- Resume должен проверять полный fingerprint серии, включая версии и модельные артефакты; сейчас проверяются путь модели, cache, residual, max_new_tokens и input hash. Замена окружения или весов по тому же пути может смешать разные условия.
- Общий конфиг матрицы и runner для новых моделей/датасетов. Сейчас DATASETS зафиксированы на трёх наборах, family prepare — на исходных n80/seed2027, а Slurm и scoring имеют специализированные пути. Новый набор пока нельзя корректно подключить одной заменой имени в командной строке.
- Фиксировать primary contrasts, правило остановки и размер final series заранее. Дополнительные проверки маркировать как exploratory; при множественных формальных тестах использовать подходящую коррекцию.
- Архивировать сырые результаты и manifest вне временного scratch. Для публичного пакета достаточно scores/predictions/IDs/provenance без весов и скопированных исходных документов, с учётом условий исходных данных.

cd ~/kv-cache-longbench-pilot

  --results-dir results/families/qwen3-4b/retrieval80 \
  --out-dir results/families/qwen3-4b/summary \

  --results-dir results/families/qwen3-4b/retrieval80
