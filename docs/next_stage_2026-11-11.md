**Следующий шаг на кластере — аудит реальной истории, без GPU.**

```bash
cd ~/kv-cache-longbench-pilot
git pull --ff-only
module load python
conda activate kvcache
python -m src.audit_expansion
```

Скрипт не скачивает данные и не запускает модели. Он проверяет SHA-256
`data/raw/longbench-data.zip`, исключает опубликованные пилоты, сканирует
`data/prepared/**/*.jsonl` и `results/**/*.jsonl`, а также archive hashes manifest.
Если у старого результата нет context hash, он восстанавливается по dataset
и source_index из того же архива. Входы, подготовленные, но ещё не оценённые,
консервативно считаются использованными.

Вывод содержит доступные вопросы и уникальные документы по шести наборам.
Отчёт сохраняется в `results/expansion_audit_2026-11-11.json`. Показаны также
ошибки и полнота локальной истории; повреждённые JSONL и несогласованные hashes
не игнорируются. При ошибках или отсутствии истории аудит не считается пройденным.
Предыдущий отличный отчёт не перезаписывается: для обновления после новых запусков
нужно задать другой `--output`.

Для каждого набора создаётся только предварительный список: uniform sample
контекстов, затем один вопрос на контекст, seed 2031, максимум 80 документов.
Эти списки ещё не являются готовым manifest GPU-серии. Перед подготовкой нужно
выбрать задачи, проверить пересечения между выбранными наборами, зафиксировать
промпты/лимиты, модельные token IDs и условия. Exact hashes не обнаруживают
перефразы, переводы и частично совпадающие документы; неизвестные/несохранённые
запуски невозможно исключить автоматически.

**Предлагаемая следующая GPU-серия после аудита.**

Если доступны 80 новых retrieval context, взять их и 80 новых документов
HotpotQA. Это одновременно независимая проверка прежнего retrieval-эффекта
и перенос на multi-document QA. Альтернатива второго набора — Qasper
для single-document QA; категории заданы в
[официальном описании LongBench v1](https://github.com/THUDM/LongBench/blob/main/LongBench/README.md).
Выбор фиксировать до просмотра результатов новой серии.

Вариант с тремя уже имеющимися моделями — Qwen3-1.7B, Qwen3-4B, SmolLM3-3B:

**3 модели × 2 набора × 2 prefill × 4 cache × 80 документов = 3 840 новых ответов.**

Cache: Dynamic/g16/g32/g64; общий residual=512 при подтверждённом запасе
query+answer и отсутствии refresh. Native chat/no-thinking, FP16/SDPA,
одинаковые входные IDs внутри модели и явно зафиксированные пределы генерации.
Это новая серия, проверяющая переносимость при подавленном refresh; изменение
набора и buffer не интерпретируется как отдельный причинный эффект данных.

Более узкий вариант только с двумя Qwen — **2 560 ответов**. Он проверит границу
по размеру, но оставит семейство без нового независимого контроля. Поэтому
при доступных ресурсах предпочтителен вариант с тремя моделями. После аудита
нужны отдельный manifest, smoke всех условий и оценка GPU-времени по реальным
логам/таймингам. Этот документ не отправляет задания; runner новой серии
подготовлен в [отдельном протоколе](expansion_protocol_2026-11-11.md).
Окружение ради неё обновлять не требуется.

**Отдельные последующие оси.**

- Язык: retrieval EN/ZH позволяет начать с двух языков, но это разные документы
  и распределения. Разность качества не изолирует влияние языка; для такого
  вывода нужны согласованные примеры или отдельные контролируемые переводы.
- Механизм: общий teacher-forced префикс и K-only/V-only на небольшой заранее
  зафиксированной выборке, без выбора только самых плохих примеров.
- Эффективность: resident KV bytes, peak allocations, prefill/decode timing
  на одинаковых длинах и железе. Эти выводы не следуют из quality-таблиц.

Добавлять одновременно новые модели, языки, длинные ответы и все задачи LongBench
пока не требуется. Независимые документы плюс один новый QA-поднабор дают
конкретный следующий результат при понятном объёме вычислений.
