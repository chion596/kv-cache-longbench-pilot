**План следующей серии: смешанная точность K/V, 15 ноября 2026 года.**

Статус: runner, проверки и команды подготовлены; GPU smoke ещё не выполнялся.
[Актуальный протокол](mixed_precision_protocol_2026-11-15.md).
Текущая завершённая серия — [kv_probe_v1](kv_probe_results_2026-11-15.md).
Её [CPU-диагностика завершена](kv_probe_diagnostics_2026-11-15.md): крупный
g64-эффект сохраняется при исключении любого одного документа, а forced/native
поведение различается. Следующий шаг — только smoke mixed_precision_v1.

**Гипотеза.** Если в проверенных HQQ-настройках основная чувствительность
связана с K, то K8/V4 должен лучше сохранять native-качество, чем K4/V8,
при сопоставимом фактическом размере cache. K16/V4 проверяет более дорогой
вариант с точными ключами. Улучшение forced-NLL само по себе эту гипотезу
о качестве свободных ответов не подтверждает.

**Зафиксированная матрица.** Две Qwen, retrieval EN и HotpotQA, прежние
80 expansion_v1 документов на набор, только context_then_question,
группа 64, residual=512, native chat без thinking, FP16/SDPA, ответ до 32 токенов.
Три новые политики: K8/V4, K4/V8, K16/V4. Ещё два условия — свежие Dynamic
и K4/V4. Всего **20 ячеек и 1 600 native-генераций**, из них 960 для новых
политик и 640 повторных контролей. Это 160 уже изученных документов.

Dynamic и K4/V4 пересчитываем в новой серии на всех 80 входах. Старые
expansion_v1 ответы используются только для диагностики drift, а не как
знаменатель новых quality-контрастов. Все входы и source hashes проверяются.
Не смешиваем двадцать teacher-forced проб и native-ответы в одну метрику.

**Фиксированный бюджет памяти.** Для одинакового числа N элементов K и V
идеальный payload относительно полного FP16 KV (4N bytes):

| Политика | Идеальный payload / FP16 KV |
|---|---:|
| K4/V4 | 25% |
| K8/V4 | 37.5% |
| K4/V8 | 37.5% |
| K16/V4 | 62.5% |

Это арифметика битности, **не измеренная память и не экономия общей GPU RAM**.
В реальности есть scales/zeros, packing, точный residual и временные tensors.
Сравнение K8/V4 и K4/V8 при одинаковом номинальном payload — главный контроль;
одна политика K16/V4 против K4/V4 меняет и точность, и объём памяти.

До заявления о равном бюджете нужно посчитать реальные уникальные GPU tensor
storages cache: quantized data, metadata и точные состояния, без двойного
учёта views/aliases. Измерять в одинаковой точке, после вопроса перед первым
decode-шагом. Peak allocator memory с весами модели не заменяет cache bytes.
Длительности свободных ответов разной длины также не являются чистым
сравнением throughput; latency требует отдельного фиксированного сценария.

**Проверки до full.** Смоук должен сверить одинаковые K4/V4 и K8/V8
с stock HQQ соответствующей битности, K16/V16 с Dynamic, убедиться, что
разные K/V действительно имеют нужную точность и refresh отсутствует.
Проверять одинаковые input IDs, свободную генерацию и реальные cache bytes.
В новой серии не добавляем forced-префикс ответа. Новые конфигурация, manifest,
исходники и каталоги результатов сохраняются отдельно от kv_probe_v1.

**Результат.** Официальные retrieval_score / QA F1 и парные документные
контрасты K8/V4−K4/V8, K8/V4−K4/V4, K16/V4−K4/V4. Рядом — абсолютные
Dynamic baselines, resident cache bytes, EOS/лимит и корректность первого
номера retrieval. Для HotpotQA повторить общую необрезанную sensitivity
подвыборку, поскольку расхождения truncation между моделями уже известны.

Новые политики на этих 80 документах дают следующий этап разработки,
а не независимое подтверждение после выбора политики по результатам.
Для подтверждения лучшего варианта потребуется новый заранее зафиксированный
набор либо репликация на иной задаче/модели с явным учётом выбора гипотезы.

**Масштаб и бюджет.** 1 600 native-генераций — содержательное расширение:
проверяем качество исправления и реальную память вместо повторения того же
детерминированного запуска. Оценку времени снимаем с нового smoke; 0.282
GPU-часа teacher-forced серии напрямую на свободную генерацию не переносим.
Подготовлен массив из четырёх job, до двух GPU одновременно, как в прошлых
сериях. Full отправляется отдельно после полного smoke и проверки cache bytes.
