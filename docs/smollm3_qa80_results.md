# SmolLM3-3B: LongBench multifieldqa_en, 80 заданий

Дата: 27 октября 2026 года.

## Исследовательский вопрос

Переносится ли наблюдавшаяся на `passage_retrieval_en`
устойчивость SmolLM3-3B к HQQ INT4 `q_group_size=64`
на длинные задачи QA, где требуется сгенерировать содержательный
ответ, а не только одно число?

**Результат:** на 80 одинаковых исходных заданиях
`multifieldqa_en` разница g64−Dynamic равна
**−2.376 п.п.**, парный 95% bootstrap
**[−6.324; +0.885] п.п.**. У Qwen3-1.7B в ранее
проведённом контролируемом сравнении на тех же
исходных 80 заданиях падение g64−Dynamic составляло
**−12.945 п.п.** Но у SmolLM3 отсутствие статистически
надёжной разницы **не доказывает эквивалентность**.

## Официальные результаты LongBench QA F1

| Кэш | Официальный F1 | 0 F1 | Генерации до лимита | Средняя длина |
|---|---:|---:|---:|---:|
| Dynamic | **40.087%** | 5/80 | 22/80 | 36.0 токенов |
| INT4 g16 | **39.823%** | 5/80 | 23/80 | 36.7 токенов |
| INT4 g64 | **37.710%** | 4/80 | 25/80 | 38.4 токена |

| Парный контраст | Разница, п.п. | 95% percentile bootstrap |
|---|---:|---|
| g16 − Dynamic | −0.264 | [−3.107; +1.878] |
| g64 − Dynamic | −2.376 | [−6.324; +0.885] |
| g64 − g16 | −2.113 | [−5.164; +0.777] |

Метрика — `qa_f1_score` оригинального LongBench;
каждая задача оценена на том же `task_id` и тех же
token IDs **внутри** SmolLM3. Интервалы — парный
percentile bootstrap, 2000 повторов, seed 2026.
Корректировку на множественные сравнения не делали.

## Контраст с Qwen3-1.7B на QA EN

| Кэш | Qwen3-1.7B | SmolLM3-3B |
|---|---:|---:|
| Dynamic | 24.622% | 40.087% |
| INT4 g16 | 24.732% | 39.823% |
| INT4 g64 | 11.677% | 37.710% |
| **g64 − Dynamic** | **−12.945 п.п.** | **−2.376 п.п.** |

**Оговорка:** это не чистый эксперимент на влияние
семейства модели, поскольку различаются число параметров,
обучение, tokenizer и поведение генерации. Несмотря на
совпадение исходных LongBench заданий, длина входа в
токенах и token IDs у моделей различаются.

## Диагностический контроль: F1 только первой строки

Для каждых из тех же 80 ответов дополнительно
рассчитан F1 **первой непустой строки**, не меняя
оригинальные файлы JSONL.

| Кэш | Исходный F1 | F1 первой строки | Выигрыш после отсечения |
|---|---:|---:|---:|
| Dynamic | 40.09% | 47.45% | +7.36 п.п. |
| INT4 g16 | 39.82% | 47.45% | +7.63 п.п. |
| INT4 g64 | 37.71% | 47.34% | +9.63 п.п. |

Грубая разница между g64 и Dynamic на первом ряду
равна **−2.376 п.п.**, а по первым строкам
около **−0.11 п.п.**. Последнее — сравнение
постобработанных ответов, **не официальный балл LongBench**.

Число задач, в которых F1 первой строки
повысился/снизился относительно полного ответа:

- Dynamic: 9 улучшений, 2 ухудшения.
- g16: 9 улучшений, 2 ухудшения.
- g64: 13 улучшений, 3 ухудшения.

Яркие примеры лишней генерации:
- `multifieldqa_en:137`: первая строка `1766`,
  F1 полного ответа 5.71%, первой строки 100%.
- `:49`: `48V`, исходная оценка Dynamic 5.71%,
  первой строки 100%.
- `:54`: `30,223`, исходная оценка Dynamic 4.26%,
  первой строки 100%.
- `:7`: g16 и g64 начинают с правильного
  `Vice Admiral`, но много лишнего текста снижает
  F1 соответственно до 10.81% и 7.69%; по
  первой строке у обеих 100%.

Контрпримеры:
- `:82`: первая строка даёт F1 0% при ненулевой
  оценке полного ответа.
- `:8`: ответ g64 `2–0` остаётся неверным,
  но длинное продолжение случайно даёт 20.69% F1
  по официальному токеновому перекрытию.

**Нельзя** заключать, что ошибки из-за квантизации
исчезли: отсечение первой строки — постфактум-выбор
правила форматирования. Ранние фактические ошибки
могут оставаться, а в 3 заданиях g64
первую строку удалять было вредно.

## Более строгая проверка без GPU

Добавлен `src.score_qa_continuations`:
он проверяет совпадение task IDs, входов и настроек,
а затем считает по задачам три парных контраста:
1. `raw_delta`: полный F1 квантизованной
   конфигурации минус Dynamic;
2. `first_line_delta`: F1 первых строк
   квантизованной конфигурации минус Dynamic;
3. `difference_of_deltas`: насколько отсечение
   продолжения больше помогает квантованному ответу,
   чем Dynamic, на одних и тех же заданиях.

Для каждого контраста будут рассчитаны парные
95% bootstrap-интервалы. **Их чисел пока нет**;
они появятся после запуска на сохранённых JSONL
на кластере:

```bash
cd ~/kv-cache-longbench-pilot
git pull --ff-only
source cluster.env.example
python -m unittest discover -s tests -v
python -m src.score_qa_continuations
```

Скрипт сохранит CSV в
`results/families/smollm3-3b/summary/`.

## Условия опыта

- Модель: `HuggingFaceTB/SmolLM3-3B`, FP16.
- GPU: NVIDIA V100 32GB, batch size 1.
- Greedy decoding, prefill целиком + decode через cache.
- DynamicCache или stock Transformers QuantizedCache
  с HQQ INT4, `axis_key=axis_value=1`,
  `residual_length=128`, группа 16 или 64.
- Три × 80 = 240 сохранённых ответов,
  LongBench `multifieldqa_en` (held-out seed 2027);
  фиксированные source indices и task hashes.
- Промпт: raw официальный шаблон LongBench,
  без chat template; максимум 16 384 токена.
- Генерация: до 64 новых токенов либо EOS.
- Это **подвыборка** LongBench, а не официальный
  полный результат LongBench.

## Ограничения и следующие проверки

- Отсечение ответа является постпроцессингом; следует
  отдельно проверить **фактическую** остановку генерации
  раньше, с теми же задачами и фиксированными правилами.
- QA F1 измеряет token overlap, а не исключительно
  корректность факта, поэтому полезен ручной разбор
  заданий с несовпадающими результатами.
- На retrieval у SmolLM3 сильной деградации g128
  не наблюдается, но g128 для английского QA **не проверяли**.
- Для причинных утверждений о влиянии модели нужны
  дополнительные контроли, например Qwen3-4B на
  той же retrieval-подвыборке. Такой тест частично
  контролирует семейство, но не обучение/архитектуру
  во всех деталях.
- Отдельно сравнить качество, саму KV-память и
  память модели: `torch.cuda.max_memory_allocated()`
  измеряет пик выделенной CUDA-памяти, а не
  только размер KV Cache.
- Сырые JSONL не публикуются в GitHub и остаются
  на кластере; их необходимо резервно копировать.
