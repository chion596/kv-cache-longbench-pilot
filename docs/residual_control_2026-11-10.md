**Серия residual_v1: вклад refresh в split retrieval.**

**Статус на 11 ноября: smoke и full завершены; получены 320 полных ответов.**
[Результаты и следующий этап](residual_results_2026-11-11.md).
Ниже сохранён протокол для воспроизведения.

Мотивация — [диагностика g32](group_size_diagnostics_2026-11-10.md):
у 1.7B при split теряется и официальный score, и правильность первого номера;
у 4B g32 остаётся точным. В прежних retrieval-ответах часто происходит refresh.

Проверяем гипотезу: исключение refresh после добавления вопроса меняет
качество дальнейшей генерации. **Первый токен при residual=128 и 512 должен
совпасть**: к моменту его выбора вопрос уже обработан, но длинный residual
ещё не был сброшен. Само чтение приближённого документного cache остаётся
в обеих постановках; более длинный residual не восстанавливает исходные K/V
документа из первого prefill.

| Ось | Значения |
|---|---|
| Модели | Qwen3-1.7B, Qwen3-4B |
| Задача | passage_retrieval_en |
| Prefill | context_then_question |
| Cache | HQQ INT4 g32, g64 |
| Изменение | residual_length: 128 → 512 |
| Входы | прежние 80 вопросов и token IDs |
| Объём | 4 ячейки × 80 = 320 новых ответов |
| Smoke | 4 ячейки × 3 = 12 ответов |

512 превышает известный максимум query+answer: 393+32=425 токенов.
Проверка запаса длины выполняется для всех 80 задач до отправки smoke;
счётчики затем должны показать ровно два `_quantize` на слой — исходные K и V,
без повторного обновления. Отсутствие refresh нельзя считать установленным
только на основании значения флага.

Сохраняются FP16/SDPA, native chat с thinking=False, оси 1, greedy и лимит
32 токена. Используются прежние модельные файлы и prepared manifest.
Baseline residual=128 берётся из полных protocol_v1/g32 JSONL; содержимое
исходных результатов фиксируется SHA-256. Новый runner использует тот же
общий greedy_generate, не меняя код и результаты завершённых серий.
Тип GPU, CUDA, версии пакетов и хеши общего кода должны совпасть с baselines.

На login-узле:

```bash
cd ~/kv-cache-longbench-pilot
git pull --ff-only
module load python
conda activate kvcache
bash tools/start_residual.sh smoke
```

Порядок ячеек: 0 — 1.7B g32, 1 — 1.7B g64, 2 — 4B g32, 3 — 4B g64.
До отправки проверяются все baselines, входы, общий код и версии пакетов.
На задачу одна V100, максимум два задания одновременно. Логи:
`logs/lb-residual-v1-<job>_<cell>.out` и `.err`.

После завершения всех четырёх smoke-ячеек:

```bash
python -m src.score_residual --phase smoke
```

Проверки: полная матрица, неизменность входов и условий, отсутствие refresh
во всех слоях, совпадение первого токена с тем же cache при residual=128.
Если проверка не проходит, сначала разбираем причину. Величина качества
на трёх вопросах не используется для выбора варианта или остановки по результату.
Локальная численная проверка механики cache использует искусственную квантизацию
на маленькой CPU-модели; реальный HQQ/FP16/V100 подтверждает только этот smoke.

После успешного smoke и просмотра ответов:

```bash
bash tools/start_residual.sh full
```

Full дополнительно проверяет неизменность условий относительно smoke
на login-узле и в каждом GPU-процессе. Он не запускается автоматически.
После завершения всех ячеек:

```bash
python -m src.score_residual --phase full
cat results/residual_v1/summary/full/paired_contrasts.csv
```

Каталоги: `results/residual_v1/{smoke,full}` и `results/residual_v1/summary/`.
Основные четыре сравнения — официальный retrieval_score residual512−128
отдельно по моделям и группам. Первое число — вспомогательный контраст.
Также описательно показываем Dynamic/g16, взаимодействие эффекта residual
с группой и прямое различие его эффекта между моделями. CI — парный bootstrap
по документам, 2 000 повторов, seed 2026, без коррекции множественных сравнений.

Если качество восстановится, это укажет на вклад политики refresh/residual
в этой постановке. Больший buffer одновременно сохраняет больше точных
состояний и откладывает повторное округление; эти механизмы ещё не разделены.
Если провал сохранится, refresh не будет достаточным объяснением, но ширину
интервала нужно учитывать. Отсутствие заметной разницы не доказывает эквивалентность.
Память и скорость при residual512 потребуют отдельного сопоставимого измерения.

Этот контроль уточняет механизм на прежних документах. Следующее масштабирование
данных должно использовать независимые context или новый тип QA, с проверкой
доступного числа документов и пересечений с предыдущими пилотами.
